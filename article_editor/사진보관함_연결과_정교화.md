# 사진 보관함 연결과 기사 생성 정교화

## 이번에 반영한 것

- 부제목을 2~3개의 짧은 줄로 생성하도록 출력 구조와 지침을 변경했습니다. 줄마다 18~35자를 목표로 하며 42자를 넘으면 유효한 결과로 받지 않습니다. 기자가 직접 작성하는 길이는 제한하지 않습니다.
- 전달받은 부제목 3세트와 사진 설명 4개를 문체 예시로 사용합니다. 예시의 인물·수치가 다른 기사에 섞이지 않도록 현재 원고와 구분합니다. 이것은 프롬프트 예시 반영이며 모델 재학습이 아닙니다.
- 사진 설명은 확인된 날짜·장소·주체·행동과 관련 배경을 1~3문장으로 작성합니다. 확인된 사실이 적으면 짧게 작성합니다.
- 촬영일·출처·출처 표기 방식은 별도 저장합니다. 예: `설명. 2026.9.22 ⓒ 뉴스1` 또는 `설명. [AP/뉴시스] 2026.9.24`.
- 사진 박스 전체를 잡아 이동하며 문단 사이 삽입 위치를 반투명 영역으로 표시합니다. 입력 중인 원고와 저장 데이터에 이 영역이 섞이지 않도록 제외합니다.
- 글 흐름은 상단 도구에서 여는 오른쪽 패널로 이동했습니다. AI가 번호를 써도 화면에서 제거하고 목록 번호를 한 번만 표시합니다.

## 1. Supabase 연결 순서

현재 앱은 브라우저 IndexedDB에 저장합니다. 아래 파일은 연결을 준비한 SQL과 모듈이며, 현재 화면에 Supabase 로그인을 연결한 상태는 아닙니다.

1. Supabase 프로젝트를 만듭니다.
2. Authentication에서 사용할 로그인 방식을 선택합니다. 팀 프로젝트에는 이메일 로그인 또는 팀에서 정한 로그인을 권합니다.
3. SQL Editor에서 `integration/supabase_setup.sql`을 한 번 실행합니다. 사진 원본용 비공개 버킷 `article-photos`, 사진 정보 테이블 `photo_assets`, 로그인 사용자별 접근 규칙을 만듭니다. 같은 정책명을 두 번 실행하면 오류가 나므로 완료 여부를 먼저 확인하세요.
4. 프론트 프로젝트를 만들 때 `npm install @supabase/supabase-js`를 실행합니다. 현재 Python 서버에는 추가 패키지가 필요하지 않습니다.
5. Project URL과 publishable key로 클라이언트를 만들고 로그인합니다. `service_role` 또는 secret key는 브라우저에 넣지 않습니다.
6. 로그인된 클라이언트를 동봉한 `photo_storage.js` 함수에 전달합니다.
7. 파일 선택 시 원본 File을 `uploadOriginalPhoto`에 전달합니다. DB에는 파일 주소와 설명·출처·촬영일·확인 정보를 저장합니다. Base64 본문 전체를 DB에 넣지 않습니다.
8. 보관함은 `listPhotoAssets`로 읽고, `previewPhotoURL`의 1시간짜리 URL로 표시합니다. 만료되면 다시 발급합니다. 서명 URL 자체를 영구 주소로 저장하지 않습니다.
9. AI 사진 설명에는 `originalPhotoBlob`으로 받은 원본을 현재 앱의 data URL로 변환하여 전달할 수 있습니다. 원본 파일을 변형할 필요는 없습니다.

이 규칙은 **본인 사진만 읽고 쓰는 방식**입니다. 팀 전체가 공유하려면 `teams`, `team_members` 테이블과 팀원 접근 정책을 먼저 추가해야 합니다. 버킷을 public으로 바꾸는 방식으로 해결하지 마세요.

다음 연결 작업에 필요한 정보: Project URL, publishable key, 개인 보관함/팀 공유 여부, 로그인 방식. OpenAI API 키와 Supabase secret/service_role 키를 채팅에 보낼 필요는 없습니다.

## 2. 인물 이름을 캡션에 반영하는 방법

얼굴만 보고 인물을 식별하는 기능은 포함하지 않습니다. 기자가 확인한 이름·직함·위치 관계 또는 통신사의 원본 사진 설명을 사진마다 연결합니다.

`확인된 사진 정보` 입력 예:

> 통신사 원본 설명에서 확인: 왼쪽은 A 장관, 오른쪽은 B 위원장. 2026년 9월 22일 서울의 회의실에서 회의에 참석 중. 기자가 확인한 정보만 사용.

이 확인 정보와 사진에서 관찰되는 행동을 함께 사용합니다. 원고에 인명이 나온다는 이유만으로 그 사람이 사진에 있다고 단정하지 않습니다. 이름·직함은 변할 수 있으므로 촬영 당시 정보와 확인 출처도 보관합니다.

권장 데이터: `photo_id`, `original_caption`, `verified_people`, `verified_location`, `shot_date`, `source`, `verified_by`, `verified_at`.

## 3. 헤드라인·부제목·사진 설명을 정교화하는 순서

### A. 편집 전후 데이터를 모으기

`editorial_dataset_template.csv`의 열을 기준으로 수집합니다. 사용 권한이 있는 기사·사진·캡션으로 구성합니다.

- 생성 시점 본문과 기자가 확정한 제목·부제목을 같은 행에 저장합니다.
- AI 최초 결과, 기자 수정 결과, 수정 이유, 모델·프롬프트 버전을 함께 보관합니다.
- 사진 설명용 데이터는 실제 사진, 확인 정보, 기자 확정 캡션을 묶습니다. 원고와 무관한 통신사 설명을 정답으로 섞지 않습니다.
- 본문이 바뀌면 제목의 정답도 달라질 수 있어 본문 버전을 함께 남깁니다.

### B. 평가 세트를 먼저 고정하기

프로젝트 시작안: 사람이 검수한 예시 약 100건과 별도 평가 기사 30건부터 시작합니다. 이는 프로젝트 운영 제안이며 서비스의 최소 학습 요건이 아닙니다.

같은 사건의 후속 기사나 동일 원고가 예시와 평가 양쪽에 섞이지 않게 event_id로 묶어 분리합니다. 나중 날짜의 기사를 평가용으로 남기면 실제 사용 환경을 더 잘 반영합니다.

평가 항목:

- 원문에 없는 사실·인명·수치 추가 여부
- 기사의 핵심 포함 여부와 과장 여부
- 부제목 2~3줄 충족률, 제목과의 중복
- 사진 설명의 확인되지 않은 이름·장소·촬영일 추가 여부
- 기자가 그대로 채택한 비율, 수정한 글자 수, 최종 확정까지 걸린 시간
- 요청당 비용과 응답시간

문구가 정답과 동일한지만 평가하지 않습니다. 같은 사실을 다른 표현으로 잘 전달할 수도 있습니다.

### C. 예시 검색과 프롬프트 개선

검수된 기사에서 현재 기사와 분야·구성이 비슷한 예시 2~4건을 찾아 생성 지침에 추가합니다. 예시의 사건 내용은 현재 기사에 사용하지 않도록 명시합니다. 모델에 보여준 예시와 평가 결과를 기록하고, 고정 평가 세트에서 이전 버전과 비교합니다.

이번 ZIP에는 고정 문체 예시가 반영됐습니다. 자동 예시 검색(RAG), 편집 이력 데이터 수집, Supabase 동기화는 추후 연결 대상입니다.

### D. 모델 재학습은 가용성을 확인한 뒤 결정

2026-09-26 확인한 OpenAI 공식 문서에는 파인튜닝 플랫폼이 단계적으로 종료 중이며 신규 사용자는 접근할 수 없다고 안내되어 있습니다. 따라서 새 프로젝트는 OpenAI 파인튜닝을 필수 전제로 삼지 않는 것이 좋습니다. 기존 이용 가능 계정은 계정 지원 범위를 확인해야 합니다.

우선 예시·평가·검색 기반 개선을 진행하고, 향후 실제 재학습이 필요하면 지원되는 서비스나 모델을 그 시점에 검토합니다. 수집한 입력·정답·수정 데이터는 이 과정에서도 재사용할 수 있습니다.

## 기존 사용자가 업데이트하는 방법

실행 중인 터미널에서 Ctrl+C → 기존 폴더의 index.html과 server.py만 새 파일로 교체 → 기존 .env는 유지 → `py server.py` 재실행 → 같은 주소에서 새로고침.

자동 저장 원고는 같은 브라우저와 같은 주소를 사용해야 이어집니다. localhost와 127.0.0.1은 브라우저 저장소가 서로 다릅니다.


### 실제 크기를 바꾼 기사 이미지 파일

현재 로컬 화면은 원본을 유지하고 동아일보용 최대 가로 684px, 네이버용 최대 가로 666px 파일을 브라우저에서 생성해 내려받게 합니다. 미리보기에서도 플랫폼별로 생성한 파일을 사용합니다. Supabase 예시 연결 코드는 원본 업로드만 다룹니다. 팀 서비스에서 가공본까지 저장하려면 파일마다 플랫폼·픽셀 크기·원본 사진 ID를 연결하는 스토리지 경로/DB 열을 추가한 뒤 업로드 로직을 붙여야 합니다.
