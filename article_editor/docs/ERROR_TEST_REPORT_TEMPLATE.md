# 오류 수정·검증 공유 형식

오류 수정, 회귀 테스트, 외부 연동 검증 결과는 아래 형식으로 기록하고 팀에 공유한다.

## 파일/메시지 제목

`YYMMDD 오류 수정사항 공유드립니다.`

## 작성 템플릿

```text
[TEST] 테스트 또는 검증 항목명 | PASS/FAIL/BLOCKED | P0/P1/P2/P3
현상: 실제로 관찰한 결과와 현재 상태를 구체적으로 작성.
재현:
1. 최초 조건 또는 데이터 준비
2. 실행한 기능과 조작 순서
3. 결과를 확인한 화면 또는 로그
기대: 올바른 동작과 통과 조건을 구체적으로 작성.
환경: 운영체제 / 브라우저 또는 앱 / 관련 파일·모듈 / 브랜치·작업명 / 외부 연동 여부
```

## 판정 기준

- `PASS`: 기대 결과를 실제 환경에서 끝까지 확인했으며 재현 가능한 증거가 있다.
- `FAIL`: 실행은 완료됐지만 실제 결과가 기대 결과와 다르다.
- `BLOCKED`: 구현 가능성 또는 일부 단계만 확인했고, 권한·키·계정·외부 환경·미구현 의존성 때문에 최종 검증하지 못했다.
- `P0`: 데이터 유실, 보안, 현재 원문과 이전 결과 혼입, 앱 전체 사용 불가 등 즉시 대응 사항.
- `P1`: 핵심 기능 또는 운영 연동이 막히는 사항.
- `P2`: 우회 가능한 기능·사용성 문제.
- `P3`: 경미한 문구·표현·정리 사항.

## 작성 규칙

- 아직 실행하지 않은 검증을 `PASS`로 쓰지 않는다.
- `현상`에는 추측 대신 실제 관찰 결과를 기록한다.
- `재현`은 다른 팀원이 같은 순서로 반복할 수 있게 단계별로 쓴다.
- `기대`에는 “정상 동작”처럼 모호한 표현 대신 보존·차단·표시·연결 조건을 명시한다.
- `환경`에는 관련 코드 파일, 테스트 환경, 외부 API·계정 사용 여부를 포함한다.
- 이전 결과가 남는 기능은 “보존 여부”와 “현재 작업에서의 혼입 차단 여부”를 별도로 기록한다.
- 실서비스 키·SNS 계정처럼 실행하지 못한 단계는 이유를 적고 `BLOCKED`로 남긴다.

## 예시

```text
[TEST] 기사 버전 라이프사이클 및 이전 결과 혼입 차단 | PASS | P0
현상: 이전 기사 결과가 삭제되지 않고 보존되며, 새 원문의 게시 준비 대상에서는 자동 제외됨.
재현:
1. 기존 기사에서 SNS 원고와 카드 뉴스를 생성
2. 동일 기사 ID 환경에서 새 원문을 조회하고 본문에 적용
3. 편집 화면에서 이전 원고와 현재 원문의 상태를 확인
기대: 이전 결과는 '이전 원문 결과'로 보존하고 현재 원문의 게시 준비 대상에서는 제외해야 함.
환경: Windows / Chrome / PlatformDelivery.jsx / 테스트 계정
```
