# 저장 설계: 로컬 경로 규칙 · 보관함 · 데이터맵 (2026-10-18, 같은 날 적용)

대상: 이 앱을 고치는 개발자와 다음 주 사용자 테스트를 준비하는 팀.
범위: 사용자가 앱으로 **올리는(가져오는) 파일**과 **내려받는(내보내는) 파일**이 어디에 놓이는지, 그리고 보관함·데이터맵이 무엇을 어떻게 저장하는지.
로그 트래킹은 이 설계 다음 단계다. 로그 자리(`%LOCALAPPDATA%\AI Newsroom\logs\`)만 정해 둔다. (2026-10-21: 동의 기반 사용자 테스트 기록은 `logs\` 가 아니라 계정 저장소의 `ut_events` 표에 들어간다 — §7-3)

## 1. 원칙 다섯 가지

1. **원고와 자료는 암호화 저장소 한 곳에만 둔다.** 계정마다 파일 하나(`vault-<사용자 id>.db`, SQLCipher)다. 평문 원고를 디스크·`localStorage`에 두지 않는다.
2. **가져온 파일은 복사본으로 저장한다.** 원본 파일은 읽기만 하고 고치지 않는다. 원본 경로도 기억하지 않는다(나중에 원본을 옮기거나 지워도 앱 자료는 그대로).
3. **사용자가 볼 파일은 `내 문서\AI Newsroom\`, 앱만 쓰는 파일은 `%LOCALAPPDATA%\AI Newsroom\`.** 섞지 않는다.
4. **암호를 푼 임시 파일은 정해진 임시 폴더에만 만들고, 앱 시작·종료 때 지운다.**
5. **내보내기는 사용자가 누른 경우에만 평문을 만든다.** 이름 규칙을 지켜서 같은 폴더에서 찾기 쉽게 한다.

## 2. 폴더 지도

### 지금 (코드 기준, `article_editor/app/app_paths.py`)

| 위치 | 내용 | 비고 |
|---|---|---|
| `%LOCALAPPDATA%\AI Newsroom\vault-<user>.db` (+`-wal`, `-shm`) | 원고·이력·발행본·고정본·취재자료 원본·녹음·녹취·사진·데이터맵 Markdown·임베딩 | 암호화. 기기 키는 Windows 자격 증명 관리자 |
| `…\vault-<user>.before-restore.db` | 백업 복구 직전 안전 복사본 | 복구할 때마다 덮어씀 |
| `…\settings.json` | 환경 설정(클라우드 백업, AI 엔진, 자동 로그인) | 평문, 비밀 없음 |

| `…\webview\`, `…\sns\`, `…\factcheck\` | 웹뷰 프로필, SNS 브라우저 프로필, 판정 캐시 | 앱 전용 |
| `…\open\<자료 id>\` | 취재자료를 외부 프로그램으로 열 때 만든 **복호화 임시본** | 다음 열기·시작·종료 때 지움 |

## 3. 가져오기(업로드) 규칙

| 무엇을 | 어디서 | 저장 위치 | 한도 | 형식 |
|---|---|---|---|---|
| 취재자료 파일 | 기사 작성 > 근거자료 | `sources` 표(원본 BLOB + 추출 글자) | 30MB/파일 | PDF·DOCX·HWP·HWPX·TXT |
| 녹음 | 인터뷰·녹취 | `transcripts` 표(음성 BLOB + 대화) | 40MB/파일 | 오디오·비디오 |
| 사진 | 기사·카드 편집 | `media` + `media_assets` 표 | 25MB(직접 올림), 15MB(Unsplash) | JPG·PNG·WEBP |
| Markdown 노트 | 데이터맵 > 파일/폴더 추가 | `knowledge_files` + `knowledge_links` 표 | 5MB/파일, 한 번에 100개 | `.md` |
| 이동식 백업 | 환경 설정 > 백업에서 복구 | 저장소 전체 교체(직전 안전 복사본 남김) | 160MB | `.db` (사용자 암호) |

규칙:
- 앱은 **파일 내용만** 받는다. 원본 경로는 저장하지 않는다. 데이터맵 폴더 가져오기만 **폴더 안의 상대 경로**(`기획/a.md`)를 남긴다. 링크 해석과 역할 분류에 필요하기 때문이다.
- 같은 상대 경로를 다시 가져오면 **갱신**한다(새로 만들지 않음). 지금 동작과 같다.
- 한도를 넘거나 형식이 다르면 저장하지 않고 이유를 화면에 보인다. 일부만 실패하면 성공한 것은 남기고 실패 목록을 보인다.

## 4. 내보내기(다운로드) 규칙

**결정 D2(적용):** (A) 고정 폴더 + 폴더 열기. 코어 `POST /api/exports`(core/exports.py)가 쓰고 `POST /api/exports/open`이 탐색기로 연다. 브라우저 개발 실행도 같은 코어 경로를 쓴다.

이름 규칙(A·B 공통):
- `YYYYMMDD[-HHMM]_<기사 제목 앞 30자, 공백→-, 파일명 금지 문자 제거>_<무엇>.<확장자>`
- 같은 이름이 있으면 덮어쓰지 않고 ` (2)`를 붙인다.
- 카드뉴스는 기사마다 하위 폴더를 만들고 `01.jpg`부터 번호를 붙인다.
- 백업 파일에는 기사 제목을 넣지 않는다(파일 이름으로 내용이 새지 않게).

## 5. 보관함 저장 체계

### 지금
- 보관함 목록 = 기사마다 **마지막 수동 저장본**(`article_revisions` 의 `kind='manual'` 최신 줄). 아직 수동 저장 전이면 자동 저장본.
- 이력: 수동 저장마다 한 줄, 자동 저장은 "마지막 수동 저장 뒤 한 칸"을 덮어씀. 기사당 최근 200줄.
- 발행본: `article_published` 에 기사당 한 줄(다시 발행하면 덮어씀).
- 고정본: `article_snapshots`, 검증·변환 근거라 트리거로 수정·삭제를 막음.
- 삭제: `article_deleted` 에 표시만 남기고 **내용은 영원히 남는다**.
- 상태: `draft`(발행 전) / `published` / `editing`(발행 뒤 고침). 원고 JSON 의 `status` 문자열이 따로 또 있다.

### 문제
1. "삭제"해도 원고·이력·사진이 암호화 저장소에 그대로 남는다. 저장소가 커지고, 사용자가 "지웠다"고 믿는 것과 다르다.
2. 상태가 두 군데(계산된 `state`와 원고 안 `status`)에 있어 어긋날 수 있다.
3. 사진(`media`)은 어떤 원고도 쓰지 않게 돼도 지워지지 않는다(고아 사진).

### 적용
- **상태는 하나만:** `state`(코어 `storage.article_state`) 하나가 기준이다. 저장할 때 원고 JSON 의 `status`는 버리고, 원고를 돌려줄 때 코어가 `작성 중|송고됨|수정 중`으로 채운다.
- **삭제 = 휴지통:** 지우면 보관함에서 빠지고 "휴지통"에 30일 보인다(되살리기 가능). 30일 뒤 앱 시작 때 영구 삭제한다. 대상은 이력·발행본·처음 저장 시각, 그리고 다른 원고가 쓰지 않는 사진. **결정 D1(적용):** 영구 삭제 때 고정본도 지운다. 같은 트랜잭션 안에서만 트리거를 잠시 풀고 바로 되돌린다(`storage.purge_trash`). 영구 삭제는 로그인 때 저장소 준비 단계에서 돈다. 휴지통으로 옮기면 서버 백업 사본도 바로 지운다(영구 삭제한 기사가 서버 복구로 되살아나지 않게).
- **고아 사진 정리:** 영구 삭제 때 `media` 중 어떤 원고·고정본도 참조하지 않는 줄을 지운다(`storage.py:197`의 shortcut 해소).
- **목록 규모:** 지금은 전부 한 번에 읽는다(수백 건까지). 사용자 테스트 규모에서는 그대로 둔다.

## 6. 데이터맵 저장 체계

### 지금
- 노드 = 기사(보관함과 같은 목록) + 업로드 자료(`sources`) + 고정본 + Markdown 노트(`knowledge_files`) + 끊긴 링크(미확보).
- 연결 = 기사→자료(최신 저장본이 쓰는 자료), 기사→고정본, 노트→노트(`[[링크]]`·`[](경로)`). 비슷함 점수나 추측 연결은 만들지 않는다.
- 노트의 **분류(기획·원자료·인터뷰·검증)는 화면이 폴더 이름으로 추측**한다(`src/features/data-map/constants.js`의 `CATEGORY_FOLDERS`).
- 노트는 복사본이다. 원래 폴더의 파일을 고쳐도 다시 가져오기 전에는 바뀌지 않는다.
- 업로드 자료와 Markdown 노트가 **서로 다른 종류**라, 노트는 팩트체크 근거로 쓸 수 없고 업로드 자료는 링크를 가질 수 없다.

### 문제
1. 분류 규칙이 화면에만 있어, 같은 노트가 다른 화면·보고서에서 다르게 분류될 수 있다.
2. 사용자는 "자료"를 하나로 생각하는데 저장은 두 종류다(`sources`, `knowledge_files`).
3. 다시 가져오기 말고는 원래 폴더와 맞출 방법이 없다.

### 적용
1. **분류를 코어에 저장:** `knowledge_files.role`(SCHEMA_VERSION 6, `article|plan|data|interview|verify|note`). 가져올 때 `knowledge_files.ROLE_FOLDERS` 규칙으로 정한다. 옛 노트는 이전 때 한 번 채운다. 화면 규칙(`CATEGORY_FOLDERS`)은 지웠다. 화면에서 손으로 바꾸기는 아직 없다.
2. **자료 하나의 목록:** 표는 그대로 두고 읽기 모델이 `resources`(`kind: file|note`, `role`)로 함께 내보낸다. 데이터맵 화면은 "자료 목록"으로 보여 준다. 노트를 팩트체크 근거로 색인하는 일은 아직 하지 않았다.
3. **원래 폴더와 맞추기(D3, 권장안 적용):** 복사만 하고, 노트가 있으면 폴더 버튼이 "다시 가져오기"가 된다. 같은 폴더를 고르면 바뀐 파일만 갱신한다. 실시간 연결은 하지 않는다(원본 경로를 저장해야 해서 원칙 2와 부딪힘).
4. **삭제 연동:** 기사를 휴지통에 넣으면 데이터맵에서도 빠진다(지금과 같음). 노트를 지우면 그 노트를 가리키던 링크는 "미확보"로 바뀐다(지금과 같음).

## 7. 남은 일

1. 노트 역할을 화면에서 손으로 바꾸기, 노트 본문을 팩트체크 근거로 색인하기.
2. 원고 내보내기(.docx/.txt)는 아직 없다. 만들면 `exports.KINDS`에 `원고` 종류를 더한다.
3. 로그 트래킹: 저장·내보내기·휴지통·영구 삭제 지점에 이벤트를 남긴다(`logs\`). 원고 내용은 넣지 않는다.
   - 2026-10-21 현재: 저장·다시 열기·내보내기·코어 작업 성공/실패·플랫폼 변환 결과·화면 이동은 **사용자 테스트 기록**(`ut_events`, 동의한 계정만, 암호화, 7일·10,000건)으로 남는다. 같은 이벤트를 Google Analytics 로도 보낸다(동의한 계정만, 기사·실행 ID 제외, 대기열은 코어 메모리 — 보안 모델 §5-9). 휴지통·영구 삭제 이벤트는 아직 없다.
