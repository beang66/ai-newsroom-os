# 보안 모델 — 데스크톱 앱 (자산 · 경로 · 규칙 · 백로그)

- 상태: **구현 반영(2026-10-13)** — 2026-10-02 초안에서 암호화 저장소·계정별 분리·로그인 유지·원고 백업 암호화 등을 구현한 현재 상태로 갱신
- 범위: 로컬 우선 데스크톱 앱(웹뷰 + App Core)과 우리 백엔드/Supabase 연결
- 관련: `../ARCHITECTURE.md`(키·접근 경계), `IPC_MIGRATION.md`(전송), `../../APP_CORE_ARCHITECTURE.md`(Core 구조), `../../docs/team/TEAM_TEST_GUIDE.md`(사용자 안내)

## 1. 전제

> **앱(코어 포함)은 신뢰 경계가 아니다.**
> 운영키·비밀키는 앱에 넣지 않는다. 앱에는 "백엔드 주소 + 사용자 토큰"만 둔다.

"로컬에 있으니 안전하다"는 가정을 걷어내고, **어디서 무엇이 나갈 수 있는지**를 명시한 뒤 우선순위를 정한다.

## 2. 자산 (무엇을 지키는가)

| 자산 | 어디에 있나 | 노출 시 피해 |
|---|---|---|
| **원고·취재자료·녹취·사진** | 계정별 암호화 저장소 `vault-<계정 id>.db` + AI·검색 호출 시 일부 전송(§5) | 기사 내용 자체, **기자·취재원 위험** |
| 로그인 토큰 | 액세스 토큰은 코어 메모리, **갱신 토큰은 "로그인 유지"를 켠 때만** Windows 자격 증명 관리자 | 그 사용자 권한(액세스 토큰은 짧음, 서버에서 폐기 가능) |
| 기기 키(저장소 암호화 키) | Windows 자격 증명 관리자 | 이 PC 의 모든 계정 저장소 복호화 |
| 운영키(OpenAI, Cloudflare, `service_role`) | **백엔드에만** | 전체 데이터·과금 |
| 앱 무결성 | exe·업데이트 | 개조본 유포, 자격 탈취 |

## 3. 신뢰 경계

```
[웹뷰]  ← 가장 노출. XSS·서드파티 스크립트·확장·원격 콘텐츠. 토큰은 모른다.
   │ 계약(api.*)만 — 창에서는 pywebview 브리지(core/coreBytes 두 메서드), 브라우저에서는 HTTP
[App Core] ← 같은 프로세스. UI보다 신뢰하지만 **기기 소유자에게는 비신뢰**(개조·덤프 가능)
   │ HTTPS
[백엔드(Render) / Supabase(Auth, RLS)] ← 최종 판정자. 권한·과금·한도를 여기서 결정
```

## 4. 위협 모델

| 공격자 | 무엇을 얻나 | 현재 완화 | 남은 위험 |
|---|---|---|---|
| 클라우드 침해 | 저장된 것 | 원고·자료는 **서버에 저장하지 않음**(Supabase 는 인증 계정만, 백엔드는 무저장 프록시) | 서버 저장·공유 기능을 도입하면 암호화·키 관리 필요(S1) |
| 웹 콘텐츠 취약점(XSS·확장·원격 스크립트) | 페이지가 볼 수 있는 모든 것 = **원고 포함** (토큰은 코어 보관으로 차단) | 계약 경계, 브리지는 `core`/`coreBytes` 만 노출(토큰 반환 메서드 없음) | **CSP·원격 콘텐츠 금지 미적용** |
| 폴더 복사·수리·중고·백업 업로드 | 로컬 파일 | 저장소는 SQLCipher 암호화, 저장 위치가 동기화 폴더가 아닌 `%LOCALAPPDATA%`, 키는 사용자 PC 의 OS 자격 증명 저장소 | 같은 Windows 사용자 안에서는 키를 읽을 수 있음(아래 §11) |
| 같은 PC 의 다른 앱 계정 | 다른 계정의 기사·자료 | 계정마다 저장소 파일이 따로라 앱 안에서 닿지 않음 | **기기 키가 같아 PC 단위 보호는 아님** — 파일 접근 권한이 있으면 복호화 가능 |
| 기기 소유자·개조 | 토큰, 로컬 평문(실행 중), 백엔드 주소 조작 | 운영키는 앱에 없음 | 토큰 수명·폐기 정책은 백엔드 과제 |
| 악성코드·원격 접속·사내 DLP | 실행 중 메모리, 화면 | 없음(로컬 암호화로도 실행 중엔 무효) | 앱 잠금·세션 타임아웃 미구현 |
| 네트워크 도청·중간자 | 전송 중 원고·토큰 | HTTPS | 인증서 고정(pinning) 미적용 |

## 5. "기기 탈취 없이" 나가는 경로

"원고는 로컬이니 기기를 뺏기지 않는 한 안전하다"는 성립하지 않는다. 실제 경로와 상태:

| # | 경로 | 상태 |
|---|---|---|
| 1 | **AI 호출 자체가 원고 전송** | 제목·부제 추천(기본 OpenAI), 사진 키워드, 흐름 요약은 **본문 전체**를 보낸다. `store:False`, 백엔드 프록시는 무저장. 팩트체크 외부 재검토는 문장 + 근거 조각 최대 3개. **로컬 팩트체크를 끄면 모든 문장**이 외부 모델에 간다(설정) |
| 2 | **임베딩 검색** | 팩트체크의 자료 검색을 위해 **모든 자료 조각과 문장**이 백엔드(Render)를 거쳐 Cloudflare Workers AI 로 전송된다(저장 안 함). 전송 범위 축소는 SEC 후속 과제 |
| 3 | **웹뷰는 원고를 반드시 안다** | 토큰은 감췄지만 원고는 브리지·HTTP 응답으로 반환됨 → CSP 미적용이 곧 원고 노출 위험 |
| 4 | **사진 검색** | 검색어가 Unsplash 로 전송된다 |
| 5 | **로컬 평문 흔적** | §6 의 임시 복호화본·웹뷰 프로필·안전 복사본 |
| 6 | **실행 중 메모리·원격 접속·DLP** | 범위 밖(§11) |
| 7 | **공유 기능**(예정, S1) | 규칙만 존재: 평문 업로드 금지, 암호문만 서버에, 기사는 자동 공유·취재자료는 공유 요청 |

## 6. 현재 저장 실태 (사실 · 근거)

| 저장물 | 위치 | 상태 |
|---|---|---|
| 기사·수정 이력·고정본·취재자료 원본·사진·녹취·팩트체크 기록·임베딩 캐시·지식 파일 | `%LOCALAPPDATA%\AI Newsroom\vault-<로그인 계정 id>.db` | **SQLCipher(AES-256) 암호화**, 계정마다 별도 파일. 키는 랜덤 32바이트, Windows 자격 증명 관리자에 보관(`vault.py`). 열 수 없으면 새 키를 만들지 않고 실패(fail closed) |
| 로그인 상태 | 액세스 토큰: 코어 메모리. 갱신 토큰: **로그인 유지를 켠 때만** 자격 증명 관리자(`saved_login.py`) | 비밀번호·액세스 토큰은 저장하지 않음. 로그아웃하면 지운다 |
| 강제 종료 대비 원고 백업 | 웹뷰 IndexedDB, 계정별 칸 | **AES-GCM 암호화**(키는 코어가 기기 키·계정 id 에서 파생, 화면 메모리에만). 저장이 끝나면 지운다 |
| 웹뷰 프로필 | `%LOCALAPPDATA%\AI Newsroom\webview\` | 자동 완성 기록(`Web Data`)은 앱 전후로 삭제. 그 밖의 캐시·설정은 남으므로 폴더 전체를 민감정보로 취급 |
| 설정 | `settings.json`(평문) | 설정값만(클라우드 백업·로컬 팩트체크·공용 자동 로그인 토글). 토큰·내용 없음 |
| 로그 | `logs/app.log`, `logs/storage-errors.jsonl` | 원고·키 미기록. 저장 실패 기록은 시각·작업 종류·예외 종류·errno 만 |
| 외부 프로그램용 임시 복호화본 | `open/` | **평문 임시 파일**(자료 원본을 기본 프로그램으로 열 때만 생성). 앱 시작·종료 때 삭제 |
| 이전 안전 복사본 | `vault.pre-accounts.db`, `vault-<id>.before-restore.db` 등 | 기기 키로 암호화된 DB 사본. **자동으로 지우지 않는다**(사용자가 정리) |
| 사용자 백업 | 사용자가 정한 위치 | 사용자 암호로 다시 암호화한 SQLCipher 파일(12자 이상, 최대 160MB). 기기 키는 포함하지 않음 |
| 계정 도입 전 평문 파일 | 옛 `articles/`·`sources/` 폴더 | 암호화 저장소로 가져오지만 **원본 파일은 지우지 않는다**(사용자가 확인 후 정리) |
| 팩트체크 라우팅 로그 | `factcheck_routing_events.jsonl` | **기본 꺼짐**(`FACTCHECK_ROUTING_LOG=1` 일 때만, 문장·근거가 평문으로 남으므로 개발용) |

확인 도구: `packaging/scan_plaintext.py <프로필> <표식>`(저장소 밖 평문 흔적 검사), `packaging/run_clean_profile.ps1`(실제 데이터와 분리된 빈 프로필 실행), `dev/tests/backup-encryption-probe.mjs`(실제 브라우저에서 백업 암호화 확인).

## 7. 구현 규칙 (코드 리뷰 체크리스트)

1. **운영키·secret을 앱(코어 포함)에 넣지 않는다.** 앱이 아는 것은 백엔드 주소 + 사용자 JWT뿐이다. (`AI_BACKEND=local`은 개발 전용, 배포본 기본은 remote)
2. **브리지(`js_api`)에 토큰을 반환하는 메서드를 만들지 않는다.** 노출은 `core(path, payload)`/`coreBytes(path)` 두 개뿐이며 경로 검증은 HTTP 와 같은 `Handler`를 거친다. 화면이 받는 비밀은 계정별 원고 백업 키(파생키)뿐이다.
3. **웹뷰에 원격 콘텐츠·외부 스크립트를 로드하지 않는다.** (CSP 적용은 백로그 P2)
4. **원고·사진·토큰을 로그·크래시 리포트·에러 메시지·진단 정보에 남기지 않는다.** 문제 보고용 진단 정보에는 이메일·내용·경로의 사용자 이름을 넣지 않는다.
5. **클라이언트 주장을 신뢰하지 않는다.** 권한·과금·한도는 서버가 최종 판정.
6. **전송은 최소 정보만.** 외부로 나가는 범위는 §5 에 적고, 바뀌면 문서·사용자 안내(`TEAM_TEST_GUIDE.md`)를 함께 고친다.
7. **로컬에 남기는 평문은 §6 에 적는다.** 새 저장 위치를 만들면 이 문서에 먼저 올리고, 가능하면 암호화 저장소에 둔다.
8. **실패 시 안전(fail closed).** 자격·암호화·검증 실패는 통과시키지 않는다. 예: 로그인하지 않으면 자료 요청은 401 `AUTH_REQUIRED`.
9. **시험은 실제 사용자 데이터·계정을 건드리지 않는다.** 새 테스트는 `core`보다 `env_isolation`을 먼저 import한다(고정 사용자·임시 저장소). 로그인 준비·저장소 이전은 UUID 형식의 계정 id 에서만 한다.

| P1 | **로컬 저장 암호화** | **완료** — SQLCipher 계정별 저장소, 키는 OS 자격 증명 저장소, 사용자 백업·복구, 로그인 필수 |

| SEC | **임베딩 요청의 자료 전송 범위 축소** | 후속 과제(d5): 지금은 모든 조각이 Cloudflare 로 전달됨 |
| SEC | 가입 범위 제한 | 후속 과제: 이메일 확인을 꺼 두어 누구나 가입 가능. 관리자·팀 명단(S1)에서 정함 |
| SEC | 외부 호출 한도·남용 방지 | 후속 과제: 가입한 누구나 백엔드(AI) 기능을 쓸 수 있음 |

### 제품 백로그(보안 외, 합의로 이번 범위에서 제외)
- **이전 마법사**: 한 PC 의 저장소·계정을 다른 PC 로 옮기는 안내 흐름(지금은 사용자 백업·복구로 수동 이전)
- **'서버에 백업' 설정 토글의 실제 동작**: 환경 설정에 "작성 중 기사 클라우드 백업"(기본 켜짐)이 있으나 **설정값만 저장**한다. 서버 저장·공유 기능(S1)을 만들 때 이 값을 읽어 동작시킨다

## 9. 지금 상태에서 이미 되어 있는 것

- 운영키가 앱에 없음(배포 기본은 백엔드 프록시), AI 요청에 `store:False`
- 원고·키를 로그·진단 정보에 남기지 않음
- 프론트는 토큰·백엔드 주소를 모름. 브리지는 두 메서드만
- 로그인 토큰은 코어가 보관하며 `GET /api/session` 은 토큰 없이 상태만 준다. 로그인 유지는 갱신 토큰만 OS 자격 증명 저장소에 둔다
- Supabase 는 anon 키만 사용(service_role 은 백엔드 전용)
- 원고·자료는 SQLCipher 암호화 + 계정별 파일 + 로그인 필수, 강제 종료 대비 백업도 암호화
- 웹뷰 자동 완성 기록 삭제, 종료 때 임시 복호화본 삭제
- 로컬 모델은 SHA-256 검증 후에만 사용(불일치 시 파일 삭제)
- 로컬 전용 바인딩(127.0.0.1)·배타 바인딩(포트 탈취 방지)·Origin 검사

## 10. 갱신 시점

- 서버 저장·공유(S1)를 구현할 때 → §4·§5·§6 에 서버 저장물을 올리고, 키 관리·팀원 제외 시 키 교체를 정한다
- CSP·앱 잠금을 구현할 때 → §4·§8 의 남은 위험을 지운다
- 외부로 나가는 데이터(§5)가 바뀔 때 → 사용자 안내와 함께 고친다

## 11. 남은 한계 (구현했어도 막지 못하는 것)

1. **임시 복호화본**: 자료 원본을 기본 프로그램으로 열면 `open/` 에 평문 파일이 잠시 생긴다. 앱 시작·종료 때 지우지만, 앱이 강제 종료되면 다음 실행 전까지 남는다. 외부 프로그램(뷰어)이 복사본을 따로 둘 수도 있다.
2. **SSD 에서는 삭제를 보장할 수 없다**: 지운 파일·옛 암호화 DB 의 조각이 저장 장치에 남을 수 있다(웨어 레벨링). 저장소 삭제·백업 복구 시 남는 안전 복사본(`*.before-restore.db` 등)은 자동으로 지우지 않는다. 지워야 할 데이터는 **키를 폐기하는 방식**(기기 키 삭제)이 확실하다.
3. **실행 중 메모리**: 열려 있는 동안 복호화된 원고·토큰·백업 키가 메모리에 있다. 악성코드·원격 접속·메모리 덤프·사내 DLP 는 막지 못한다.
4. **같은 Windows 사용자 권한**: 기기 키는 그 사용자의 자격 증명 관리자에 있어 같은 사용자로 실행되는 프로그램이 읽을 수 있다. 계정별 저장소 분리는 앱 안에서 보이는 범위를 나누는 것이며 PC 단위 보호가 아니다.
5. **웹뷰 프로필의 그 밖의 흔적**: 자동 완성 기록은 지우지만 Chromium 의 캐시·설정 파일 전체가 민감정보가 아니라고 보장하지는 않는다. 폴더 전체를 민감정보로 취급한다.
6. **외부 서비스로 나간 내용**: §5 의 전송은 되돌릴 수 없다(저장하지 않는 정책에 의존).
