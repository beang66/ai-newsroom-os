# 콘텐츠 변환: 원문 검사·문맥 보조·Core 검색 비교 실험안

> **현재 코드 기준 실행 순서:** [개정 실행 계획](CONTENT_TRANSFORM_SEARCH_EXECUTION_PLAN_CURRENT_2026-10-14.md)을 우선한다. 아래는 최초 설계 시점의 분류·평가 기준이다. 작성 후 B0 위치 문맥과 카드뉴스 검수 재사용이 구현되어, 아래의 '현행 A', 'B0 미구현', '최종 검수에만 적용', 카드뉴스 기본 6회 및 동일 검수 재사용 없음은 현재 제품 동작 설명이 아니다. B1 고정본 검색과 실제 비교 실험은 여전히 미구현·미실행이다.

작성일: 2026-10-14 (Asia/Seoul)  
상태: **설계만 작성 / 실험 미실행 / 검색 미구현**

이 실험은 전체 원문과 플랫폼별 전체 규칙을 유지한다. 팀 Core, 생성기, 검수기, UI, 모델 설정, 저장소 스키마는 변경하지 않는다. 아래 비교군과 기록 장치는 향후 격리된 실험 환경에서 구현할 대상이며 현재 제품에 존재하는 기능으로 표시하지 않는다. 유료 API, 실제 계정·저장소, 기사 고정본 생성은 이번 작성 작업에서 사용하지 않았다.

- 방향 기준: [기존 논의 기록 6절](CORE_SEARCH_AND_PLATFORM_REVIEW_2026-10-14.md#6-platform-rulesjs를-기준으로-재검토한-방향)
- 연결 논의: [별도 계약 제안](CONTENT_TRANSFORM_SEARCH_CONTRACT_PROPOSAL_2026-10-14.md)
- 소스 기준선: [17개 관련 파일 SHA-256](CONTENT_TRANSFORM_SEARCH_BASELINE_2026-10-14.json). 파일 변경 여부 확인용이며 배포 EXE·운영 서버 버전을 뜻하지 않는다.

## 1. 먼저 구분할 오류

여기서 '현행 원문 구절 검사'는 생성 결과의 `source_evidence`가 원문에 존재하는지 검사하는 코드다. 생성 문장 전체의 의미·직접 인용·수치를 자동으로 원문과 비교하는 검사라고 확대 해석하지 않는다.

| 분류 | 오류 예 | 현재 코드의 확인 범위 | 필요한 처리 |
| --- | --- | --- | --- |
| A: 구절 존재 검사 | 근거 배열 없음·빈 근거·원문에 없는 근거 문자열 | `checkEvidence()`가 누락·불일치를 반환 | 현행 코드로 오류 발견 가능. 새 검색 불필요 |
| A: 인용 문자열 변조 | 근거에 숫자/이름을 바꾸거나 떨어진 구절을 붙여 원문에 없는 문구를 제출 | 공백 정규화 후 제목·본문 각각에서 연속 부분문자열 검사 | 검색으로 조용히 교체하지 않고 잘못된 근거로 표시 |
| A: 본문 근거 한정 | 카드뉴스 배분표에 제목의 표현만 본문 근거로 제출 | `checkInformationPlan()`은 `article.content`에서 인용 존재를 확인 | 배분표 단계의 기존 검사 유지. 모든 검수 경로가 본문 한정을 강제한다고 단정하지 않음 |
| 별도 코드 검사 | 빈 필드, 잘못된 장수·역할·태그·이모지, 배분표 ID 배정 위반 | 생성기/기본 검수의 구조 검사 | 원문 검색 불필요. ID 배정 통과는 실제 내용 충족의 증거가 아님 |
| B: 일치 위치는 알지만 인접 문맥 필요 | ‘확대한다’ 앞 문장에 ‘인력 확보 시’가 있음; 다음 문장에 예외·시행 조건이 있음 | 인용 존재 검사만으로 조건 유지 여부를 판정하지 못함 | 해당 인용 위치의 문단과 앞뒤 문단을 가져오면 됨. 추가 임베딩 없이 처리 가능 |
| B: 인용 주체·대상 불명확 | ‘그는’의 지칭이 앞 문단에 있음; 같은 발언이 여러 기관/기간에 반복됨 | 문자열 존재는 확인하나 어느 위치가 맞는지는 확정하지 못함 | 모든 일치 위치와 인접 문맥을 보존. 모호성 유지; 첫 일치만 선택하지 않음 |
| C: 다른 위치의 관련 근거 탐색 | 바꿔 쓴 주장의 연결 근거가 없거나, 첨부 근거는 실제 원문이나 다른 대상·기간의 문장임 | 현행 AI는 전체 원문으로 판단하지만 구절 검사만으로 관계를 판단하지 못함 | 원문 내부 후보 탐색의 효과를 실험. DenseFly+BM25는 후보를 제공하며 정답을 보증하지 않음 |
| C: 떨어진 조건·정정 탐색 | 관련 수치의 비교 기간, 정정 내용, 계획/확정 상태가 멀리 떨어져 있음 | 국소 위치 확장만으로 충분하지 않을 수 있음 | 전체 원문 검수를 유지하며 검색 보조 후보와 반대·예외 문맥을 함께 확인 |
| D: 전체 편집·정보 누락 | Instagram 결론이 전체 주제를 못 묶음; Threads 핵심 조건이 빠짐; 카드 본문 정보가 마지막 장에서 처음 등장 | 의미/편집 AI 검수 영역. 문자열·검색 순위로 판정 불가 | 원문 전체 + 결과 전체 + 해당 플랫폼 규칙으로 검수. 카드뉴스는 배분표와 실제 문장을 함께 확인 |

주의 예: 원문 ‘주말 운영을 두 시간 늘릴 계획’의 인용이 정확히 붙어 있어도 생성 문장이 ‘운영 시간이 늘었습니다’이면 구절 존재 검사는 통과할 수 있다. 반대로 같은 문장을 복사했더라도 문단 배치·주체·시점 때문에 오류가 될 수 있다. 완전 일치에 근거해 최종 검수를 생략하지 않는다.

## 2. 고정본을 검색 대상으로 쓸 수 있는가

**데이터는 사용할 수 있으나 현재 검색 기능으로 바로 연결돼 있지는 않다.**

| 확인 항목 | 현재 구현 | 판단 |
| --- | --- | --- |
| 고정본 내용 | `article_snapshots`에 `title`, `body_html`, `body_text`, `content_hash`, 기사/이력 ID, 부제·URL 저장 | 검색 입력은 생성·검수에 쓰는 같은 `body_text`. 별도 자료 본문이나 현재 편집 본문으로 치환하지 않음 |
| 내용 고정 | 고정본 UPDATE/DELETE 방지 트리거, 같은 내용의 고정본 재사용 | 안정적인 검색 범위 식별에 적합. 기존 해시·ID·불변 정책 유지 |
| 기존 플랫폼 연결 | `PlatformManager._from_snapshot()`이 고정본 제목·본문을 생성/검수 입력으로 사용 | 고정본을 읽는 기반은 이미 있음 |
| 저장 색인 | `source_index`/`source_chunks`는 `sources`와 연동; `index_source()`는 자료 테이블을 조회 | snapshot ID를 source ID 자리에 넣는 것으로 준비되지 않음. 고정본→청크 매핑 계약 필요 |
| 검색 함수 | `rank_chunks(query, chunks, ...)`는 호출자가 전달한 후보 집합을 처리 | 알고리즘은 재사용 가능. 공개 고정본 검색 API·UI 연결은 없음 |
| 청크 위치 | 현재 `build_material_chunks()`는 정리된 text/kind/field를 저장하고 원문 절대 offset을 보장하지 않음 | 주변 문맥·인용 위치를 위해 원문 좌표 매핑이 필요. 알고리즘 재사용과 위치 계약 추가를 구분 |
| 인용 선택표 | `sourceExcerpts()`가 문장 구절을 만들지만 중복 제거와 trim을 수행 | 현재 출력 번호만으로 원문의 모든 발생 위치·앞뒤 문맥을 복원한다고 가정하지 않음 |

추가 비용은 작업에 따라 다르다.

| 작업 | 추가 색인/임베딩 필요 여부 |
| --- | --- |
| 알려진 구절의 원문 위치·앞뒤 문단 조회 | 문자열 정규화↔원문 좌표 매핑만 필요. 벡터 색인과 임베딩 API 호출 불필요 |
| 최초 고정본 의미 검색 | 청크 생성·고정본 매핑 필요. 같은 모델·역할·정확한 청크 문자열의 벡터 캐시가 없으면 문서 임베딩 호출 필요 |
| 새로운 검색 질의 | 같은 모델·`query` 역할·정확한 질의 문자열의 캐시가 없으면 질의 임베딩 호출 필요 |
| 동일 고정본·질의 재사용 | 유효한 매핑과 벡터가 남아 있으면 추가 임베딩 없이 재사용 가능. BM25·DenseFly 문서 코드 계산/읽기 비용은 남을 수 있음 |
| 본문/제목·청킹/모델 변경 | 해당 색인/캐시 유효성 재검사. 바뀐 청크·질의만 실제 캐시 미스로 계산되지만 과거 고정본과 혼용하지 않음 |

현재 `VectorCache`의 키는 모델 ID·document/query 역할·text이며 기존 자료에 같은 텍스트의 벡터가 있으면 재사용할 가능성이 있다. 이는 **고정본 소유권·청크 위치 매핑이 이미 존재한다는 의미가 아니다.** 현재 캐시는 고정본 전용 수명 관리도 하지 않는다. 기존 라이브러리 호출 자체가 vault에 캐시를 쓰므로 향후 실험에서도 운영 vault에 연결하지 않는다.

기본 임베딩은 `/ai/embeddings` 원격 경로다. 최초 색인 시 문서 텍스트 조각, 질의 시 생성 문장 일부가 외부 처리될 수 있다. 현재 코드 배치는 최대 8문장 또는 60,000자 기준이며 병렬 요청도 각각 호출 수에 포함한다. 문서/질의 개수만으로 정확한 API 호출 수를 추정하지 않는다.

## 3. 비교군: 전체 원문과 전체 규칙을 모두 유지

| 군 | 실험 입력과 처리 | 임베딩 | 질문 |
| --- | --- | --- | --- |
| A 현행 | 현재 생성·구절 검사·사실 검수·편집/요구사항 검수 그대로 | 콘텐츠 변환용 추가 호출 없음 | 기준선 |
| B0 위치 기반 문맥 보조 | A + 첨부 근거의 모든 일치 위치에서 해당 문단·앞뒤 문단을 보조 입력으로 제공 | 없음 | 검색 없이 문맥 위치 안내만으로 개선되는가? |
| B1 Core 검색 보조 | B0 + 사전 지정한 모호/미연결 항목을 DenseFly×2+BM25/RRF로 검색해 주변 문맥 포함 후보를 보조 입력으로 제공 | 최초 문서·신규 질의의 캐시 미스 | B0보다 추가 오류 발견이 있는가? 추가 시간/토큰을 감수할 가치가 있는가? |

검색 후보는 ‘추가 사실’이 아니라 같은 고정본의 원문 위치 안내다. 생성 입력·생성 모델·전체 원문·규칙·고정본·구조 검사·기존 재시도 정책·순차 실행을 유지한다. 이 실험에서 병렬화, 모델 교체, 검수 합치기/생략, 자동 채널 파생은 함께 적용하지 않는다.

첫 실험의 보조 입력은 **최종 명시적 검수**에만 추가한다. 카드뉴스 생성 중 배분표·자동 검수·교정은 모든 군에서 현행으로 유지한다. 현재 두 검수 호출(사실→편집/요구사항)에 같은 보조 묶음을 전달하며 별도 문장별 LLM 호출은 추가하지 않는다. 카드는 배분표와 실제 전체 카드도 유지한다.

B0는 현재 문자열 검사 결과를 바꾸지 않는다. 없는/잘못된 인용은 계속 오류이며 검색된 다른 구절로 자동 교체하지 않는다. 한 구절이 여러 곳에 있으면 발생 위치를 모두 기록하고 입력 예산을 넘는 경우 불완전 안내를 명시한다.

B1의 검색 발동은 정답 라벨이나 A의 AI 결과를 보지 않고, 동일한 초안·근거에서 결정한다. 초기 후보 정책은 (1) 근거 누락/불일치, (2) 여러 발생 위치로 연결이 모호, (3) 수치·기간·조건/예정·직접 인용이 있는 필드 중 근거 연결 확인이 필요한 항목이다. 판정 규칙·우선순위·질의 분할·정확한 문자열 조건은 개발용 기사에서 고정하고 `trigger_policy_version`으로 남긴다. 이는 현재 구현된 자동 분류가 아니다.

개발용 설정 후보: 원고당 검색 대상 최대 4개, 대상당 상위 5개 본문 후보와 바로 앞뒤 청크 각 1개, 중복 제거 후 보조 입력 최대 2,000토큰. 후보 수/예산은 개발용 기사에서만 조정 후 확정한다. 인명·기간·조건을 잘라 예산을 맞추지 않는다. 제외·누락 항목을 표시하고 전체 원문 검수를 계속 수행한다. 검색 점수로 통과·오류·근거 충분 여부를 결정하지 않는다.

현재 `retrieval_score`는 RRF 융합 확신도가 아니라 Qwen 코사인이다. 검색 실패/시간 초과/색인 미완료 시 A와 같은 전체 원문 검수로 진행하고 ‘검색 보조 없음’을 기록한다. 실패 실행을 성공한 B1 집계에서 제외하지 않는다.

## 4. 플랫폼별 시험과 정답 기준

| 플랫폼 | 구절 검사 시험 | 문맥 보조 시험 | 핵심 정보·편집 품질 시험 |
| --- | --- | --- | --- |
| Instagram | 문단/closing 근거 누락·가짜 인용·근거 문자열 숫자 변경 | 인용 주체 혼동, 계획을 완료로 표현, 본문과 closing의 상태·조건 불일치 | 게시글만으로 사건 이해, 문단 설명 관계, 도입 회수, 최종 결론·주체 유지. 기본 문단 수를 강제 정답으로 삼지 않음 |
| Threads | 제목/요약 블록 근거 누락·실제 원문에 없는 구절 | 핵심 쟁점의 필수 조건 생략, 수치 기간 생략, 반말 전환 시 주장/예정의 확정화 | 합법적인 핵심 쟁점 하나와 필요한 맥락 유지, 자연스러운 반말. 관련 없는 기사 세부 생략은 오류 아님. 글자 수 권장 초과 자체도 오류 아님 |
| 카드뉴스 | 배분표 본문 근거 불일치, 카드 근거 누락, 잘못된 ID 배정 | headline/answer/detail 각각의 조건·시점 유지, 직접 인용의 본문 발언 주체, 통계 단위/기간 연결 | 원문 주요 정보의 배분표 누락, ID만 있고 설명 없음, 본문 완결, 중복, 마지막 장의 새 정보, 표지 주제 회수. 원문→배분표→실제 문장 세 단계 확인 |

공통 정상 대조 사례: 자연스러운 바꿔쓰기, 동일 의미의 단위 표기, 적절한 세부 생략, 핵심 정리를 위한 짧은 재언급. 보조 검색이 이들을 잘못 지적하는지도 평가한다.

평가 자료 제안: 기사 30건 중 6건은 설정 개발용, 24건은 고정된 최종 평가용. 짧음/중간/김, 숫자·직접 인용·계획/예외·멀리 떨어진 정정·동일 구절 반복을 고르게 포함한다. 정치적 입장·추가 배경 추측 없이 원문으로 정답을 만들 수 있어야 한다. 개인정보가 제거되고 실험 사용 범위가 확인된 자료만 사용한다.

정답은 사람 두 명이 먼저 독립 작성하고 불일치를 합의한다. 각 오류의 실제 위치·원문 근거·심각도와 플랫폼별 필수 정보 단위를 기록한다. A/B0/B1 결과의 군 이름을 가리고 평가한다. Threads는 사용자 키워드가 정한 쟁점 또는 규칙상 허용되는 선택 쟁점별 필수 정보를 정의한다. 모든 기사 세부를 공통 필수 목록으로 강제하지 않는다.

## 5. 두 실험을 분리

### 실험 I: 같은 초안으로 검수 효과 비교

1. 현행 생성기로 플랫폼별 초안을 한 번 확보하고 결과·배분표·근거를 그대로 고정한다. 생성이 실패한 경우와 생성 중 교정도 별도 기록한다.
2. 자연 발생 오류를 사람에게 라벨링한다. 각 초안에 한 가지 오류를 주입한 복사본도 만들되 A형/B·C형/D형이 전체 평가 자료에서 균형을 이루도록 배분한다. 올바른 대조 사례도 포함한다.
3. 같은 초안 복사본을 A/B0/B1에 각각 넣고 현재 두 검수를 실행한다. 원고 수정·재생성은 하지 않는다. 군 실행 순서는 기사별 무작위 배정한다.
4. 검수가 어느 오류·누락을 발견했는지, 오탐과 호출/토큰/검수 시간을 비교한다. 불확실한 사례의 추가 반복은 사전에 정한 기준으로 전 군에 동일 적용한다.

이 실험에서 **초안의 실제 핵심 정보 누락 수는 세 군이 같다.** 비교 대상은 누락의 검수 미탐률이다. 검색 보조만으로 초안 누락이 줄었다고 보고하지 않는다. 정답 근거 위치를 B에 미리 주는 실험은 별도 ‘정답 위치 제공 상한’으로만 표기하고 실제 검색 성능에 포함하지 않는다.

규모: 24기사 × 3플랫폼 × (자연 초안 + 오류 주입 복사본) × 3군 = 432회 최종 검수, 정상 두 호출 기준 864회 LLM 요청. 초기에는 평가용 6기사로 축소해 경계·오류 분류·계측을 확인한다. 실계정 실행 전에 호출/토큰 예산과 중단 상한을 정한다. 현재 실행 승인을 요청하거나 API를 호출하는 단계가 아니다.

### 실험 II: 기사 선택부터 최종 검수 완료까지

고정된 초안 재검수 시간과 실제 작업 전체 시간을 혼동하지 않기 위한 별도 실험이다.

1. 같은 기사·선택 키워드·제작 조건·플랫폼으로 A/B0/B1을 독립 실행한다. 같은 고정본 내용과 현행 생성 경로를 사용하지만 생성 결과의 확률적 차이는 기록한다.
2. 기사 선택→불러오기→명시적 적용→필요 저장/고정→생성→기존 생성 중 교정→명시적 최종 검수를 수행한다. 버튼 대기/사람 생각 시간 없이 사전 정의된 행동 순서로 진행한다.
3. 최종 검수는 한 번 완료하면 끝낸다. ‘통과할 때까지 반복’하거나 현행에 없는 자동 교정을 추가하지 않는다. 완료·수정 필요·실패·취소를 구분하고 결과의 실제 오류·누락도 사람이 확인한다.
4. 초기 3기사 × 3플랫폼 × 3군 × 2캐시 조건 = 54회 작업. 정상 기준 LLM 216회 + 필요한 임베딩이며 재시도는 추가된다. 품질 악화나 계측 실패가 있으면 규모를 확대하지 않는다.
5. 확대 시험은 평가용 기사에 대해 플랫폼·캐시별 충분한 표본을 확보한다. 표본이 적은 p95는 탐색 수치로 표시한다. A/B를 연속 실행해 앞선 군이 다음 군의 캐시를 데우지 않도록 격리 상태를 복제한다.

‘검수 완료’는 응답과 UI의 오류 목록/상태 적용까지이며 ‘검수 통과’와 다르다. 사람이 수정해서 사용 가능한 글까지의 시간은 별도 후속 지표이고 현재 자동 경로의 시간과 섞지 않는다.

## 6. 캐시 조건과 실제 추가 호출

- Cold: 이미 동일 내용의 기사 고정본 데이터는 있지만 검색 청크·관련 문서/질의 벡터가 없는 격리 상태. 새 의미 색인을 만드는 시간·문서/질의 임베딩을 모두 포함한다. 기사 저장·고정본 생성이 필요한 별도 사례도 따로 측정한다.
- Document-warm: 같은 고정본 매핑과 문서 벡터는 준비됐지만 이번 초안의 질의 벡터는 없는 상태. 실제 재편집·다른 채널 사용에 가까운 비용을 측정한다.
- Full-warm은 선택적 참고군: 문서·질의까지 이미 같은 경우. 이를 일반 처리시간으로 광고하지 않는다.
- 검수 결과 자체는 주요 비교에서 재사용하지 않는다. OpenAI 입력 캐시 사용은 끄거나 조작했다고 가정하지 않고 실제 사용량을 기록한다. 군 순서를 교차해 편향을 줄인다.
- 색인 선행 준비를 해두고 ‘기사 선택→완료’에서 빼지 않는다. 준비 시각/비용과 요청 내 추가 비용을 분리하고 최초 사용 총비용도 함께 표시한다.

## 8. 현행 호출 기준: 결과 수와 API 횟수를 혼동하지 않기

옵션 키워드 추천·사진 검색/생성·렌더·SNS는 주 시험에서 제외하고 모든 군의 키워드를 고정한다. 별도 사용 시험에서만 추가 호출로 표시한다.

| 플랫폼 | 정상 생성 경로 | 명시적 최종 검수 | 기사 선택→최종 검수 정상 LLM 요청 기준 |
| --- | --- | --- | --- |
| Instagram | 원고 1회 | 사실 1 + 편집/요구사항 1 | 3회; 생성 형식 보완이 있으면 추가 |
| Threads | 원고 1회 | 사실 1 + 편집/요구사항 1 | 3회; presentation 보완이 있으면 추가 |
| 카드뉴스 | 배분표 1 + 원고 1 + 생성 중 검수 2 | 사실 1 + 편집/요구사항 1 | 6회; 배분표 재시도·최대 두 원고 교정 및 그 검수는 추가 |

카드뉴스의 `generation_review`를 이번에 후속 검수 대신 재사용하지 않는다. 현재 UI 검수 계약은 `validation_review`를 사용하므로 중복 감소를 같은 실험에 섞으면 검색 효과를 구분할 수 없다. B0/B1은 최종 검수 LLM 요청 수를 같게 유지하지만 보조 입력으로 토큰이 증가할 수 있고, B1은 임베딩 호출이 추가될 수 있다.

## 9. 결과 표와 채택 기준

아래 표는 **미실행 양식**이며 0이나 예상 개선치를 넣지 않는다. 각 행은 Cold/Document-warm으로 나누고 실험 I/II를 별도 집계한다.

| 플랫폼 | 군 | 오류 미탐률 | 실제 핵심 누락률 / 누락 미탐률 | LLM / 문서·질의 임베딩 호출 | 토큰 구분 | 기사 선택→완료 p50/p95 | 과잉 지적·실패 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Instagram | A / B0 / B1 | 미측정 | 미측정 | 미측정 | 미측정 | 미측정 | 미측정 |
| Threads | A / B0 / B1 | 미측정 | 미측정 | 미측정 | 미측정 | 미측정 | 미측정 |
| 카드뉴스 | A / B0 / B1 | 미측정 | 미측정 | 미측정 | 미측정 | 미측정 | 미측정 |

- 관측 표본에서 새 중대한 사실 오류의 검수 누락이 생기면 원인을 분석하고 자동 적용을 보류한다. 핵심 누락·과잉 지적·원고 품질 악화도 함께 확인한다.
- B0가 같은 개선을 제공하면 추가 임베딩이 없는 B0를 우선 검토한다.
